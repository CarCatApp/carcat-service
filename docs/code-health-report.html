1Executive Summary

carland_service is the core backend of the Carland/CarCat product: it manages cars, customers, maintenance templates, service-life percentages, partner service visits (Hyper integration), photos, notifications and an admin panel. The service is functional and actively deployed, and several recent additions (webhook HMAC security, the V2 visit model) show good engineering instincts. However, the codebase carries significant accumulated debt that now slows every change and creates real production risk.

Overall assessment

The product logic is real and valuable, but the codebase is in a state where correctness depends on individual memory rather than structure: business rules are duplicated in 2–3 places, security is inconsistent per endpoint, roughly 10% of classes are dead or stubbed, and there is no automated verification. None of this requires a rewrite — the recommended path (Section 10) is a focused 4-phase cleanup that can be executed incrementally alongside feature work.

Security is split into three inconsistent regimes:

4Critical Findings (act immediately)

4.1 Token "validation" that validates nothing

jwt/CustomFilter.java — any Bearer string authenticates
The filter checks authHeader.startsWith("Bearer ") and then unconditionally creates an authenticated principal named "user". The three jjwt libraries declared in build.gradle are never used. Real user identity (user id, phone, role) is taken from client-supplied request headers (X-User-Id, phoneNumber, role), which any caller can forge. In practice, all "authenticated" endpoints are open, and any user can act as any other user by changing a header.

4.2 Admin panel: hardcoded credentials + security bypass

AdminController.java line 67 + JWTConfiguration permitAll
if ("nemet".equals(username) && "nemet".equals(password)) is the entire admin login. The credentials are committed to a repository whose history is shared; there is no hashing, rate-limiting or audit trail. /admin/** is additionally listed as permitAll in Spring Security and bypassed in the JWT filter, so the panel's only protection is this string comparison. Behind it sit the full car and customer databases plus one-click Excel exports.

4.3 Stale nested repository copy committed to git

carcat-service/ — 205 tracked files, ~42% of the repository
A complete, older fork of the project (including its own .github/workflows, Dockerfile and full source tree) lives inside the repository and is fully tracked by git. File contents have diverged from the live tree (verified by hash comparison). Consequences observed during this audit: code searches return double results, and it is easy to open and edit the dead copy by mistake. It should be deleted and git-ignored.

  • Admin Excel exports (/admin/cars/export, /admin/users/export) sit behind the hardcoded password only.

7.2 Unused classes and members (usage-verified)

  • 9 exception classes never thrown anywhere — ExpiredOtpException, InvalidOtpCodeException, RefreshTokenNotSetException, UsernameAlreadyExistException, MsmTransactionException, InviteException, WrongPasswordException, UnderageException, NotificationException. All are OTP/invite/auth concerns evidently copied from carland_auth; each still has a handler registered in the 256-line CustomExceptionHandler. UICustomExceptionHandler renders a template (invite-error) that does not exist.
  • Unused repository methods: BrandRepository.findAllByBrandName/existsByBrandName, PartnerRepository.findBySourceIgnoreCaseAndActiveTrue, ColorRepository.findAllByOrderByColorIdAsc, VisitRepository.findWithDetailsByCarAndHyperRecordId, ModelYearRepository.findAllByStatus.
  • Dead config/util: RestTemplateConfig (an empty class — no annotation, no beans), CustomImageCrop (only call sites are commented), PushCron (all schedules commented), the Mailtrap client bean (never injected), ServiceNameAz enum (entire body commented out).
  • Dead notification pipeline: CarServiceImpl.canSendNotification and buildMessage (~85 lines) are referenced only from commented code, while the live calculateAndPushNotification sends a hardcoded fake message ("oil change — 230 km left") to every car with a device token. Only the fact that its cron trigger is also commented out prevents mass fake pushes.
  • Unused DTOs: PrivacyPolicyResponse, TermsConditionsResponse (imported but never used), SuperAdmin request/response.
  • Unused controller members: CarController injects customerRepository and maintenanceTemplateRepository that are never read; ~30 @RequestHeader("Authorization") parameters across 7 controllers are accepted and then ignored.
  • Unused build dependencies: jjwt-api/impl/jackson (no JWT parsing exists), spring-boot-starter-webflux (no WebClient/Mono/Flux usage), mailtrap-java and spring-boot-starter-mail (active mail path is Brevo via RestTemplate), Lombok declared twice.

7.3 Commented-out code volume

12 blocks longer than 3 lines, the largest being ~80 and ~68 lines of legacy doctor/appointment logic in RangeServiceImpl, ~44 lines in CarServiceImpl, ~35 in MaintenanceTemplateServiceImpl, plus fully commented files (ServiceNameAz, PushCron schedules, alternate HMAC strategies). Commented code is where the real business rules currently hide — e.g. template-creation auth checks are commented out, meaning role verification for maintenance-template management is disabled in production.

8.2 API design findings

  • RPC-style verb URLs throughout: /get/brand/list, /for/car/upload, /insert/service/history, /edit/byId — no resource-oriented convention.
  • Wrong HTTP methods: reads via PUT (PUT /api/v1/car/get/record), deletes via PUT (/car/remove, /range/delete), updates via POST, and GET endpoints that require request bodies (often stripped by proxies).
  • Zero bean validation: not a single @Valid/jakarta.validation annotation in the controller or DTO trees; all validation is manual and inconsistent.
  • Entities leaked as API responses: GroupByController, NotificationController and getColors return JPA entities directly, coupling the public contract to the DB schema.
  • Version confusion: V2 history exposed as a path suffix under V1 (/api/v1/car/{vin}/service-history/v2); /webhook, /admin, /legal unversioned.
  • Three different error envelopes face integrators: webhook auth errors, global ResponseException payloads and success-shaped bodies returned with 409 (which is also used for benign no-op updates).

8.3 Hardcoded business data in enums

EnumMessagesLangValues holds 90 message constants in three languages — including leftover hospital/doctor-domain messages (HOSPITAL_NOT_FOUND, ONLY_DOCTOR_ALLOWED…) from a previous product. Five more enums hardcode translations and partner data (ServiceTypeTranslation 37 entries, ColorTranslation 19, HyperServiceMapping 23 alias mappings — one of which is ambiguous and silently returns empty on collision, EnumPartnerId duplicating the partners DB table). Adding a partner or fixing a translation currently requires a code deploy.

10Recommended Remediation Plan

The plan is ordered so that each phase is independently shippable and reduces risk before convenience. Estimates assume one experienced developer familiar with the codebase.

Phase 1 — Security & hygiene (≈ 1 week)

  1. Implement real JWT validation in CustomFilter (the jjwt dependencies are already on the classpath), or validate against carland_auth; stop trusting client-supplied identity headers.
  2. Move admin credentials to environment variables with a hashed password; add rate limiting; remove /admin/** from the public path lists.
  3. Remove the token/header logging in UserController, the mail-token print in MailTrapConfig, and the per-request System.out in the filter.
  4. Lock down or delete the public bulk exports (/customer-cars) and the test/debug endpoints (/test/hyper, /legal/get).
  5. Delete carcat-service/ from the repository and add it to .gitignore.

Phase 2 — Safety net (≈ 1–2 weeks)

  1. Re-enable tests in CI (drop -x test); add characterization tests around the percentage math and webhook ingest/update before touching them.
  2. Introduce Liquibase (already half-planned — the dependency is commented out); snapshot the current schema as the baseline; switch ddl-auto to validate.
  3. Turn off show_sql; standardize on SLF4J.

Phase 3 — Dead-code purge (≈ 3–4 days, low risk)

  1. Delete: 9 unused exceptions + their handlers, unused repository methods, empty RestTemplateConfig, PushCron, CustomImageCrop, ServiceNameAz, the SuperAdmin slice, unused DTOs, unused controller fields and ~30 ignored Authorization parameters.
  2. Remove unused dependencies (webflux, jjwt if unused after Phase 1, mailtrap, spring-mail, duplicate Lombok line).
  3. Delete or implement the return null stub endpoints; either restore or remove the commented notification pipeline and the commented template-auth checks (decide, don't defer).

Phase 4 — Structural refactoring (incremental, ≈ 3–4 weeks spread out)

  1. Extract from CarServiceImpl: a CustomerAccessGuard (kills ~14 duplications), a single PercentageCalculator (kills the triple formula), and response mappers.
  2. Move the V2 entities and service out of dto.response.v2 into entity/service; decide the V1-history sunset plan and collapse the duplicated Hyper fetch/map code into one client + one mapper.
  3. Extract shared webhook persistence support from the ingest/update twins; move Excel generation out of AdminController into an export service.
  4. Externalize legal texts (static resources or DB), translations and partner/service mappings out of Java enums.
  5. Adopt @Valid bean validation on request DTOs; stop returning JPA entities from controllers.
What NOT to do
A big-bang rewrite is not justified. The domain logic works and is encoded in this code (including in its commented-out corners). The debt is concentrated: two security fixes, one folder deletion, one god class and one duplicated integration account for most of the risk. Fix those and the codebase becomes ordinary.
